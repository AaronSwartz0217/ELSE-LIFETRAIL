这份重构后的日志，已经将“双Key架构”、“数据分层（一级/二级）”、“上下文压缩”、“长文本瓶颈”以及刚刚深度探讨的“RAG与索引的关系”全部打通。你可以直接复制存入你的笔记系统（Notion / Obsidian / 飞书文档）。---📝 项目复盘日志：AI Agent架构与海量数据处理实践日期：2026年10月6日标签：#AI架构 #Agent #RAG #上下文压缩 #数据分层 #上下文长度🎯 今日核心心法：优秀的AI应用 = 权限隔离（双Key） + 数据分层（一级/二级） + 检索增强（RAG） + 工作流控制（Agent）。绝不要把大模型当无限容量的硬盘，要把它当成“推理极快但临时记忆有限的大脑”，必须为其外挂硬盘和导航仪。---一、 核心架构设计：双Key物理隔离（已落地）· 架构模式：网站调用两个不同的 API Key，对应两个独立Agent。 · Key A（主控Agent/管理员）：参与前后端交互，负责修改网站本体代码，权限极高，低频高要求。 · Key B（子功能Agent/客服）：只查询日志记录来回答用户问题，权限极低（只读），高频低要求。· 架构优势：防止“提示词注入”导致灾难、避免“上下文污染”（修代码和查日志逻辑剥离）、实现降本增效（不同Key配置不同等级的模型）。· 进阶方向：两个Agent若需协同，可通过内部API（如工单系统）通信，Key B提需求，Key A接单执行，绝不越权。二、 数据基建模型：一级与二级数据· 一级数据（原始数据）：源码、完整系统日志、书籍原文。无损、绝对准确、体积巨大。是事实的唯一来源（Source of Truth）。· 二级数据（派生数据）：摘要、向量库（Embedding）、知识图谱、倒排索引。有损、精简、检索极快。是用于快速导航的“地图”。· 黄金工作流：用户提问 -> 检索二级数据（快速定位） -> 提取对应的一级数据（获取原文） -> 喂给大模型进行精准回答。· 核心心法：绝不能用二级数据（摘要）去回答细节问题，必然产生幻觉；必须靠二级数据导航回一级数据。三、 核心引擎：RAG（检索增强生成）深度剖析（重点）⚠️ 关键澄清：把原始数据提炼成二级数据索引，只是 RAG 的“上半场”，不等于完整的 RAG！· RAG 的全貌： · 上半场（离线建库）：原始数据（一级） -> 切块与向量化 -> 二级数据索引。 · 下半场（在线问答）：用户提问 -> 检索（Retrieval）二级索引 -> 取回一级原文 -> 增强（Augmented）Prompt -> 大模型生成（Generation）回答。· 建库的核心陷阱：“提炼”不等于“写摘要”！ · RAG 存的是“指向一级数据的坐标（索引）”，而不是“一级数据的替代品（摘要）”。 · 正确做法：按段落切分成小块（Chunking），保留完整原文，生成向量坐标。 · 错误做法：让AI总结成一段摘要存起来，用户问细节时AI答不出来。· 高级建库策略： · 保留元数据（Metadata）：必须带上时间戳、模块名、错误级别，方便先过滤（Metadata Filtering）再检索。 · 混合检索（Hybrid Search）：结合“向量搜索（语义）”与“关键词BM25（精确匹配）”，解决搜不到精确错误码（如 "Error 500"）的问题。· RAG 在双Key架构中的映射： · Key B（日志Agent）：经典RAG应用。用户提问 -> 检索日志向量库 -> 捞出具体的报错日志行（一级数据） -> 交给大模型生成。 · Key A（代码Agent）：检索相关代码片段，再交由模型修改，避免凭空捏造API。四、 难点攻坚：长文本与上下文压缩· 长文本瓶颈：盲目追求超大上下文（如1M Token）会面临“成本极高、响应极慢、迷失在中间（Lost in the Middle）”三大致命问题。· 上下文压缩：压缩必然有损（概括只是其中一种）。 · 无损压缩：删减冗余格式、滑动窗口、合并重复对话。 · 结构化压缩：强制保留文件路径、错误码、用户原话等核心实体，优于自然语言摘要。 · 角色感知压缩：针对Key A（保代码逻辑）和Key B（保检索准确性）定制不同压缩率。 · 可逆引用机制：为摘要附加指向原文的“锚点”，随时可回溯验证。五、 概念避坑辨析（基础认知）· “20B”是什么？：不是上下文长度，是参数量（Billion），代表模型脑容量/聪明程度。· 上下文长度怎么算？：单位是 Token（中文约1.5字/Token）。128K Token ≈ 8-10万汉字。上下文长度 = 输入Token + 输出Token。· 当前模型参数：DeepSeek当前版本上下文为128K，采用MoE架构（总参数量千亿，激活几十B），知识截止到2026年2月。六、 后续优化 To-Do1. 细化双轨制存储：确保系统在生成二级摘要的同时，严格保留一级原文的锚点链接。2. 升级检索策略：在Key B（日志Agent）的检索中，引入“关键词（BM25）+ 向量搜索”的混合检索，避免纯向量搜索丢失精确的日志错误码。3. 建立评测集：分别针对Key A（代码修改成功率）和Key B（日志问答准确率）建立独立测试题库，用数据驱动模型和Prompt的迭代。---当日最大收获：看透了“Agent就赋能”这类互联网黑话的本质。真正的赋能，是基于权限隔离、数据分层、RAG检索增强的扎实工程架构。RAG不是简简单单的“提炼摘要”，而是“建库导航 -> 精准检索 -> 召回原文 -> 生成回答”的完整闭环。
